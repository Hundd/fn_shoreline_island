## Seven wrong combinations and honest feedback

Encoding is BLUE/LARGE/REACTOR=0 and RED/SMALL/SCANNER=1. The following is an implementable priority matrix, with wording advisory to Learning Designer/Planner:

| Complete request | Actual primary mismatch | Truthful next action | Other wrong details |
| --- | --- | --- | --- |
| BLUE LARGE SCANNER | WHERE | Change WHERE to REACTOR; keep BLUE and LARGE | none |
| BLUE SMALL REACTOR | WHICH | Change WHICH to LARGE; keep BLUE and REACTOR | none |
| BLUE SMALL SCANNER | WHICH | Change WHICH to LARGE; then check WHERE | WHERE |
| RED LARGE REACTOR | WHAT | Change WHAT to BLUE; keep LARGE and REACTOR | none |
| RED LARGE SCANNER | WHAT | Change WHAT to BLUE; then check WHERE | WHERE |
| RED SMALL REACTOR | WHAT | Change WHAT to BLUE; then check WHICH | WHICH |
| RED SMALL SCANNER | WHAT | Change WHAT to BLUE; then check WHICH and WHERE | WHICH, WHERE |

Smallest copy alternative: always say only “Change WHAT to BLUE”, “Change WHICH to LARGE”, or “Change WHERE to REACTOR”, with a generic “Check the other details too” for multi-error submissions. This requires fewer messages, preserves correct choices, and never positively validates a wrong choice. The explicit matrix provides better next-action clarity. Both use captured submission values, not mutable current state. Wrong runs retain all choices and award nothing.

`run_request`370–375 selects red_core whenever WHAT=RED, regardless of WHICH. Historical red prop scale is2.5, matching large blue, while small blue scale is1.5. RED+SMALL therefore does not demonstrate an independently honored small red selection. Do not claim all request details map to the carried object. Smallest no-geometry approach is explicitly identify RED as the first unmatched detail and explain that this display only has one red core; avoid a result saying Pix honored SMALL. This is a learning/design decision, not a missing MCP capability. Planner/Learning Designer must accept its honest presentation before approval. If they require exact physical realization of every combination, scope widens: either transiently scale the existing red prop using current requested size and restore its full home transform on every cancellation, or add a fourth prop/binding. Neither is existing behavior; scaling needs height/pickup/sightline validation, and a new prop needs approved placement. Prefer retaining three props with explicit limited display explanation unless that weakens the agreed learning criterion. Do not silently implement either alternative.

These are source-established reachable race risks, not reproduced runtime defects.
5. Token checks prevent starting later stale moves; they do not cancel an already running `MoveTo`. Current cancel paths teleport props home via reset_props265–269.
